# 事業ごとのアカウント設計

Ranius 本体（`nijinworld/ranius-platform`）に、**NIJINアカデミー**と**ともだちじゃぱん**の
アカウントを同居させるための設計です。実装はこのリポジトリではなく、向こうで行います。

決めたこと：**インスタンスは1つ。アカウントは事業ごとに作る。**

---

## 1. なぜ同居させるか

デプロイ1つ・Firestore 1つ・Vertex のクォータ1つ・Cloud Run 3サービス。
事業ごとにプロジェクトを分けると、これが2倍になります。
12月に走らせるのは6名のパイロットで、その規模で2系統を運用するのは割に合いません。

---

## 2. いまの作りで、そのまま使えること

| | |
|---|---|
| テナントの単位 | `creator-{uid}`。**教師1人＝1テナント**（`services/platform-api/src/app.js:74`） |
| 誰が入れるか | `PILOT_TEACHER_EMAIL_SHA256S` の許可リスト。本番は fail-closed |
| データの分離 | 全リソースで `tenantId + userId` を検査。越境は存在を漏らさない404 |

**教師アカウントを並べるだけなら、改修は要りません。** 許可リストにメールのハッシュを足すだけです。

---

## 3. 足りないもの

### 3.1 事業という単位が無い

`tenant_id` は教師1人ごとなので、「この6人はともだちじゃぱん」と言う場所がありません。
そのため、いまはこれができません。

- 事業ごとの集計（ともだちじゃぱん全体の授業数、費用、担当数）
- 事業ごとの費用上限（`costPolicies/{tenantId}` は教師1人単位）
- 事業ごとのルーブリック切り替え（後述）

### 3.2 ルーブリックがデプロイ単位

`GEMINI_RUBRIC_PATH` は環境変数で、イメージに焼かれています
（`services/gemini-analysis/src/config.js:9`）。**1インスタンス＝1ルーブリック**です。

NIJINアカデミー = `nijin-core-1.0.0`、ともだちじゃぱん = `nijin-nihongo-1.0.0` なので、
**このままでは同じサービスで両方を出せません。**

救いは、**軸・キー・重みが同一**であることです（`nijin-nihongo-1.0.0` は
`nijin-core-1.0.0` をそのまま使い、行動アンカーと根拠の信号だけを変えています）。
つまり**結果の形は完全に同じ**で、切り替わるのは観察のときに読ませる文面だけです。

### 3.3 生徒アカウントが、事業に属していない

ロールは `teacher` と `student`/`learner` の2つだけで、`student` が使えるのは
キャリアミッションのAPIだけです（`services/platform-api/src/auth.js:27`）。
**保護者ロールはありません。**

## 4. 提案する形

### 4.1 claims に `org_id` を足す

```
role      : 'teacher' | 'student' | 'guardian' | 'mentor' | 'admin'
tenant_id : 'creator-{uid}'        ← いまのまま。教師1人＝1テナント
org_id    : 'nijin-academy' | 'tomodachi-japan'   ← 追加
```

`tenant_id` を事業単位に変えないのは、**既存のデータ分離をそのまま活かすため**です。
`org_id` は「どの事業に属するか」を表すだけの、上位のラベルにします。

### 4.2 事業の設定を Firestore に持つ

```
{prefix}_orgs/{orgId}
  ├ name              : 'ともだちじゃぱん'
  ├ rubric_version    : 'nijin-nihongo-1.0.0'
  ├ prompt_version    : 'class-evaluator-nihongo-0.1'
  ├ cost_policy       : { per_job_usd, monthly_usd }
  ├ allowed_domains   : []          ← オンボーディングの許可条件
  └ retention_days    : 180
```

### 4.3 ルーブリックを組織ごとに選ぶ

`gemini-analysis` は、いまリクエストに `rubric` を含めていません。
**ジョブ作成時に `org_id` からルーブリック版を解決し、analyzer に渡す**形にします。

- `contracts/` に `rubrics/{id}.json` を置き、両方の版を同梱する
- `POST /v1/jobs` が `org.rubric_version` を解決して analyzer へ渡す
- 評価結果の `model_metadata.rubric_version` に、実際に使った版が入る（いまも必須項目）

**軸が同じなので、この改修は「どの文面を読ませるか」の切り替えだけ**で済みます。
採点エンジン（`contracts/src/scoring-engine.js`）は変えません。

### 4.4 費用の上限を、事業ごとにも持つ

いまは `costPolicies/{tenantId}`（教師1人単位）だけです。
`orgs/{orgId}.cost_policy` を足し、**教師単位と事業単位の両方で止める**ようにします。

## 5. 同居させる前に、必ず塞ぐもの

### `GET /v1/teacher-profiles/:slug` の越境読み取り

`services/platform-api/src/domain.js:310` に所有者チェックがありません。
**認証済みの教師なら誰でも、他の先生の評価履歴とスコアを読めます。**

同じインスタンスに2つの事業の先生が同居する以上、ここは必ず分けます。

- 公開してよい部分（紹介・公開授業）と、
- 本人と担当メンターしか見てはいけない部分（評価履歴・スコア）

に分離します。**この修正は `fix/tenant-isolation` ブランチで進行中です。**

---

## 6. アームについて

**A/B のアームは、運営が把握するものです。先生には見せません。**

自分がどちらのアームかを知った時点で、ふるまいが変わります。
12月に測りたいのは「伴走のやり方の違い」であって、
「自分がAIアームだと思っていること」ではありません。

こちらのシステムでは、**サーバ側で落としています**（`hideArm()`）。
先生のロールでは、授業一覧・授業詳細・クラス・所見・ログイン情報のどこにも
`arm` が出ません。運営とメンターには見えます。テストで固定してあります。

Ranius 本体に同じ扱いを入れるかは、**A/B を本体側で回すかどうか**次第です。
いまの計画では、A/B の記録はこちら側で持ちます。

---

## 7. 生徒と保護者

ともだちじゃぱんは未成年が対象で、**保護者の同意が前提**です。
Ranius 本体には保護者ロールが無いので、当面はこう分けます。

| | どこで持つか |
|---|---|
| 生徒の在籍・出席・アンケート | **こちら**（`tomodachi-japan`） |
| 保護者の同意・撤回・保存期間 | **こちら** |
| 授業動画と AI 評価 | **Ranius 本体** |
| 評価結果の表示（先生向け） | Ranius 本体の Teacher Studio |

**子どもの氏名と発話は、Ranius 本体へ送りません。** 送るのは授業の映像と、
評価に必要な最小限のメタデータだけにします。
（こちらの書き出しにも、子どもの識別子は入りません）
